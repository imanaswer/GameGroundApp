| 17 | 2 Aug 2026 | **Tabs are swipe-paged.** Requested on device: swipe right from Home to reach Games. Overrides MOTION §2's "No horizontal slide" and widens §3's swipe rules. `app/(tabs)/_layout.tsx` swaps expo-router's `<Tabs>` (bottom-tabs, which cannot page) for its **top-tab navigator from `expo-router/js-top-tabs`**, with `tabBarPosition="bottom"`. **Import it from expo-router, never from `@react-navigation/material-top-tabs`:** since SDK 56 expo-router vendors its own copy and hard-errors at bundle time on a direct react-navigation import (`expo-router is no longer compatible with react-navigation`). The external route was tried first and had to be reverted — it bundles on the SDK-54 branch (expo-router 6) and does not on SDK 57. The vendored navigator needs no `react-native-pager-view`; the bundle got *smaller* (6.45→5.9 MB). The custom TabBar is behaviourally unchanged — same fill, spring icon, indicator, halo, haptic, same testIDs — but its props are now declared structurally in `TabBar.tsx` rather than imported, because expo-router types `MaterialTopTabBarProps` as `any & {…}`, which collapses to `any` and would silently un-type every field. **`lazy: false` by explicit choice** — all five tabs mount at launch so a swipe never lands on a placeholder, at the cost of five screens' queries firing on startup. **Two things to verify on a real build:** (a) cold start against M15's <2500ms budget, which this directly pressures; (b) gesture conflict with the horizontal rails on Home and the coach facility gallery — a horizontal drag there must scroll the rail, not change tab. Requested by Anaswer. | Anaswer |
| 16 | 2 Aug 2026 | **The §3 perspective tilt is suspended app-wide — `tilt` is opt-in and nothing opts in.** Supersedes Decision 15's cards-only carve-out, one control later: the same tearing was reported switching Camps/Workshops/Events, because `SegmentedControl` also renders `Press` and still took the `tilt=true` default. Fixing controls one at a time was chasing instances of a class, so the default flipped from opt-out to opt-in. Notable: six call sites had *already* been passing `tilt={false}` by hand, which reads as the effect having been quietly avoided for a while. **Provisional.** Every observation so far is from Expo Go on the SDK-54 branch (Reanimated 4.1), which is a different native binary from a shipping build — the tilt may be fine in a dev client. `Press` keeps the prop and MOTION.md §3 keeps the spec so it can be restored, but that decision needs a real build (Track B/C), not more guessing. | Anaswer |
| 15 | 2 Aug 2026 | **The §3 perspective tilt is cards-only; buttons compress on scale alone.** Reported on device: tapping a coach batch row split it into top and bottom halves that repainted separately. Cause was `Press` applying `{perspective: 600}` + `rotateX`, which promotes the view into a 3D compositing layer regardless of angle; on iOS those layers rasterize in tiles and tear. Two changes: `Press` now omits perspective entirely at rest (an untouched control was permanently 3D for a tilt that only exists mid-press), and `Button` passes `tilt={false}` so the tilt survives only where it is both visible and on a large static surface — cards. At button size a 2.4° rotateX is imperceptible; the felt feedback is the scale and the haptic. Precedent: Decision 11 dropped expo-blur from the tab bar for the same reason — a spec'd effect that does not survive contact with the device yields to the device. MOTION.md §3 revised. Reported by Anaswer; found only because the app finally ran on hardware. | Anaswer |
| 14 | 2 Aug 2026 | **Bottom sheets slide on a curve, not a spring.** `Sheet.tsx` opened with `spring.pop` (damping 14 / stiffness 220, ζ≈0.47) — a ~19% overshoot over a full screen-height travel, i.e. a visible bounce on the checkout sheet. First corrected to the spec-designated `spring.sheet` (ζ≈0.68, ~5%), still perceptibly springy on device. Resolved by moving entry/exit to `withTiming`: in on `dur.base` + `ease.exit`, out on `dur.fast`, drag snap-back on `dur.base`. Rationale: any underdamped spring overshoots by definition, and the sheet is the widest-travel element in the app, so the artifact is most visible exactly where it matters least — a payment sheet should feel deliberate, not playful. `spring.sheet` is now unused; retained in §1 for a future settle-physics consumer. Also removed the two inline durations (220/200ms) this replaced, restoring §1's "nothing inline, ever". Reported from device by Anaswer. | Anaswer |
| 10 | 26 Jul 2026 | **Razorpay = hosted Standard Checkout in a WebView** (`react-native-webview`, New-Arch-safe). Chosen over (a) `react-native-razorpay` — unsupported on RN 0.86 / New Arch, bridgeless-only — and (b) an interop shim (fragile for a solo maintainer). Rationale: zero native-module New-Arch risk (the BACKLOG "solo-maintainer outage" concern); server re-verifies the HMAC binding on `/payments/verify` and the webhook settles independently (§9.3), so the WebView adapter cannot create a money error the server won't catch.
