| 24 | 3 Aug 2026 | **The app is themeable: light, dark, or follow the system** (`Profile → Appearance`, default system). Requested by Anaswer. **This does not reverse Decision 20** — light stays the ported reference system and stays the default look; dark is *derived* from it (same key set, greys reversed, semantics re-derived), NOT the pre-port dark theme, which was built around a brand red Decision 20 deleted and would have produced a second design language wearing the same components. **Architecture, and why it is a proxy rather than a refactor:** 599 `color.x` reads across 71 files sit inside module-scope `StyleSheet.create` calls, which capture their values once at import — so a theme switch cannot work by swapping an object. `color`/`tier`/`gradient`/`shadow` are now proxies that resolve against the active scheme *at read time*, and `themed(() => ({…}))` replaces `StyleSheet.create` at module scope, building one real sheet per scheme. Together those leave every call site unchanged. The one thing a proxy cannot do is make React re-render, so each COMPONENT reads through a hook — `useThemedStyles(sheets)` / `usePalette()` — built on a `useSyncExternalStore` subscription. **A bare subscription was not enough, and finding out why cost a device round-trip:** with `reactCompiler` on, the compiler treats a module-scope `styles`/`color` as constant and caches anything derived from it, including the JSX, once per component instance. Components re-rendered and handed back their previous-palette output — a theme switch that applied to some screens and not others (compiled ones froze; ones the compiler bailed out of updated). Reading through a hook gives the compiler a reactive dependency. Same rule for module-scope helpers that read tokens: they take the palette as a parameter (`toneColor`, `activityVisuals`, `ringFor`, `checkoutHtml`), never read it themselves. Both omissions fail SILENTLY — correct on first paint, frozen after — so both are guarded by tests. Migration was an AST codemod, not 71 hand edits. **The navigator has its own theme**, which expo-router never sets — so it was `DefaultTheme`, white, permanently, and painted a white scene container and a white card behind every transition on the dark palette. It is now mapped onto our palette. expo-router's `AutoStatusBar` is keyed on the PHONE's scheme, so an app overridden to light on a dark phone lost its status-bar glyphs; ours is mounted below it and wins. **Three places a proxy cannot reach, all fixed:** a Reanimated worklet (`Press`) capturing border tones, and two module-scope constant maps (`payments`, `Profile`'s activity visuals) that resolved at import. **`userInterfaceStyle` moves from `"light"` to `"automatic"` in app.config.js — this needs a native rebuild.** While it said "light", iOS reported light to `useColorScheme()` regardless of the phone, which would have pinned the app's own "System" option to light with nothing in the JS to explain it. **Contrast is asserted per palette** (`tokens.test.ts`, `surface-contrast.test.ts` now run twice), which immediately found one asymmetry worth recording: light's "a fill token must FAIL as text" invariant is false on dark, where the same saturated mid-tone measures 9:1 — so that direction is asserted for light only rather than kept for symmetry. **Also fixed here:** `SplashGate` painted `color.bg`, which since Decision 20 meant a white field under a white mark — an invisible splash overlay in light. Fills dark enough for white initials clear the near-black page for free, so one set serves both grounds, which is also correct in principle: a user's identity colour should not change when the app does. Both floors are asserted per theme. The `_dev` catalog carries a theme switch, since DS §10.3 makes it the document made executable and the document now describes two palettes. | Anaswer |
